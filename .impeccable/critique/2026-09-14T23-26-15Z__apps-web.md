## Design Specificity Verdict

**LLM assessment (Assessment A):** Mostly generic, with real but undercut specificity wins. The seller alert card's "Necesita de ti" callout, the AI-summary sentence, and the WhatsApp-first CTA are genuinely product-specific — someone thought about the actual job. Strip those three moments away and this is a stock shadcn admin shell (sidebar + KPI row + donut/bar/area trio + audit table) that could be a churn dashboard or a support queue with the labels swapped. The wasted horizontal space on risk/alert cards (see Priority Issues) actively undercuts this further — it makes the flagship AI reasoning read as an afterthought bolted onto a template rather than the product's actual value.

**Deterministic scan (Assessment B):** CLI detector (`impeccable detect --json apps/web/src`, source-level) came back clean — exit 0, zero findings. The **browser-injected** detector (runtime DOM, after render) found 6 anti-pattern instances across 3 of 4 pages tested:
- `/login`: clean
- `/seller/alerts`: 1× `line-length` (~201 chars/line on the alert summary paragraph), 2× `nested-cards`
- `/admin/reports`: 1× `overused-font` (Geist, 100% of text)
- `/admin/alerts`: 1× `cramped-padding`, 1× `overused-font`

This split (clean source scan, findings only at runtime) is expected, not a contradiction — Tailwind's cascade and actual rendered text only exist post-render, so the two tools see different things by design.

**Cross-validation — this is the most useful part of running both assessments:** the `line-length` finding on `/seller/alerts` is the *mechanical fingerprint* of the exact same root cause Assessment A flagged independently as a P1 (no `max-width` on card content) — one assessment measured it as wasted layout space, the other as an overlong text line, from the same missing constraint. That agreement is why it's the lead issue below.

**False positive:** both `nested-cards` hits are pattern-matching noise, not real nested `<Card>`s — verified against `apps/web/src/features/alerts/components/alert-card.tsx`, which is a single shadcn `Card` with standard `CardHeader`/`CardContent`/`CardFooter`; the detector is reacting to `CardHeader`'s `rounded-t-xl` and `CardFooter`'s `rounded-b-xl border-t bg-muted/50` styling as if they were independent cards.

**Likely non-issue:** `overused-font` (Geist, 100%) fired identically on two unrelated admin pages, consistent with a deliberate site-wide single-font choice (Geist ships zero-config with Next.js and was chosen intentionally per the project's own architecture notes) rather than a page-specific bug. Not actioned below.

**Browser evidence:** confirmed via script injection + console read on all 4 tested pages (mutation preflight passed on every page); no separate visible on-page overlay was distinguished from the console output, so treat this as console-level evidence rather than a persistent visual overlay.

## Overall Impression

Individually, every screen is clean and unfussy — nothing looks broken at a glance. The gap is proportion and follow-through: content built for a narrow mobile-first card was never given a ceiling for desktop, so the app's actual point of difference (KEOM's AI reasoning on each alert) ends up visually equal in weight to a phone number, surrounded by empty space. The single biggest opportunity is the one two independent checks agreed on without prompting: cap card content width and let the reasoning breathe instead of the whitespace.

## What's Working

1. **`ScoreCircle`'s colorblind-safe design** (`apps/web/src/components/shared/score-circle.tsx`) — the risk score is a rendered number inside the ring, not a color-only signal, with a code comment documenting this was a deliberate accessibility decision, plus `role="img"` + a full `aria-label`. Worth protecting in any redesign.
2. **The seller alert card's information order** (avatar → name/phone → priority → value → AI summary → required action → CTA) mirrors how a human would actually triage a WhatsApp handoff — the one place content order feels authored rather than templated.
3. **Dark-mode color remapping mostly holds** — the donut, score-circle rings, and status badges all keep saturated, legible colors in dark mode instead of just inverting to gray (which makes the one place it *doesn't* hold — the primary button, below — stand out as a real miss rather than a pattern).

## Priority Issues

**[P1] Primary CTA loses visual dominance in dark mode**
- **What**: `AlertCard`'s "Abrir en WhatsApp" button uses the default `Button` variant, which rides the semantic `--primary` token. Light mode: `--primary: oklch(0.205 0 0)` → solid black-on-white, unmistakable. Dark mode: `--primary: oklch(0.922 0 0)` → near-white, and the button reads as a pale, secondary-looking pill against the near-black page (verified in `packages/ui/src/theme/globals.css`).
- **Why it matters**: This is the flagship screen's only CTA, on the one screen whose entire job is funneling the seller into one action. Weakening it in dark mode undermines the core task-completion moment for a real share of sellers.
- **Fix**: Give this button an explicit brand-colored variant (WhatsApp green, or KEOM's own `--success` green already in the token set) that doesn't ride `--primary`, so theme switching can't invert it.
- **Suggested command**: `$impeccable harden`

**[P1] Card content has no max-width — wasted desktop space and overlong text (cross-validated by both assessments)**
- **What**: Measured live at 1280px: `RiskCard` is 992px wide; the `flex justify-between` row holding the risk badge and "Valor potencial" leaves a ~750px empty gap between them (badge right edge x=333, value left edge x=1083), because the card's actual content never needs more than ~440px. Same pattern in `AlertCard`. The detector independently caught the other half of this: the alert summary paragraph renders at ~201 characters on one line with no wrap constraint.
- **Why it matters**: This is the measurable version of "feels generic" — content designed for a narrow container, stretched to desktop with no second column or width cap, so the app's actual value (the AI reasoning) reads as sparse rather than considered.
- **Fix**: Cap content width (e.g. `max-w-2xl` on the paragraph, or a fixed-width column instead of `justify-between`) or move to a 2-column card grid on desktop.
- **Suggested command**: `$impeccable layout`

**[P1] Admin alerts table has no responsive affordance on mobile**
- **What**: At 375px, the "Hora" and "Estado" columns — the two that answer "is this urgent and is it resolved" — are clipped off-screen. The container scrolls (`overflow-x-auto`, confirmed via `scrollWidth` 558px in a 341px `clientWidth`), but nothing signals that: no shadow, no fade, no scrollbar, no hint. Separately, the detector flagged the same container's outer wrapper (`<div className="rounded-xl border">` in `apps/web/src/app/admin/alerts/page.tsx`) as `cramped-padding` — it has zero padding of its own, unlike every other card on the site (`p-4`/`p-3`), so content sits flush against the border.
- **Why it matters**: An admin checking alerts on a phone can't see status or timing without discovering, by accident, that the table scrolls sideways.
- **Fix**: Add `p-2`/`p-4` to the wrapper for consistency with other cards, and either switch to stacked cards below a breakpoint (matching the pattern already used for seller/risk cards) or add a persistent scroll-shadow affordance.
- **Suggested command**: `$impeccable adapt`

**[P2] Keyboard focus ring is effectively invisible on dark-mode header icon buttons**
- **What**: Tabbing to the profile-menu button, computed styles show a focus ring (`box-shadow ... oklab(0.556 .. / 0.5) 0px 0px 0px 3px`) — but at 50% opacity, mid-gray, against the near-black header, it does not render visibly.
- **Why it matters**: A keyboard-only user has no reliable way to see which control is focused in exactly the theme (dark) this app explicitly supports — a WCAG 2.2 non-text-contrast gap on focus indicators specifically.
- **Fix**: Raise focus-ring opacity/width for icon-only buttons on dark surfaces, or pair the ring with a visible background/border change on focus.
- **Suggested command**: `$impeccable harden`

**[P3] Donut and bar chart speak two different color languages on the same screen**
- **What**: `/admin/reports`'s "Por qué se pierden oportunidades" uses a 6-color palette + legend; "Recuperación por servicio" beside it renders every bar in flat black/white regardless of service, and the donut's center hole shows no total.
- **Why it matters**: Two charts, same screen, same system, different color grammar — reads as pasted-together rather than one designed report.
- **Fix**: Either color the bars by service (reuse the donut palette) or drop color from the donut and unify on one accent + neutral scheme; consider a total in the donut's center.
- **Suggested command**: `$impeccable polish`

## Persona Red Flags

**Sam (accessibility-dependent — screen reader + keyboard-only)**
- The header's profile/theme-toggle buttons have a focus ring that exists in CSS but isn't visually perceivable in dark mode (P2 above) — Sam tabbing through the header loses track of position entirely.
- The admin alert detail page presents customer/seller/reason/timestamps as plain paragraphs under uppercase labels with no list semantics and no landmark separating fields — a screen-reader user gets a flat stream of label/value pairs with no structural way to jump between them.

**Riley (deliberate stress tester)**
- "Abrir en WhatsApp" both mutates server state and opens a new tab in the same click handler, guarded only by `disabled={acknowledge.isPending}` — a double-click before the first render settles is exactly the kind of race Riley goes looking for.
- The risk filter's zero-result state was never exercised in this session (mock data only has 3 fixed customers) — no `EmptyState` wiring was found in that specific filter path, so a search that matches nothing is untested territory.

**Casey (distracted mobile user)**
- On the mobile admin alerts table, the two most decision-relevant columns (Hora, Estado) are off-screen by default with no scroll cue — Casey, glancing at a phone between other tasks, would plausibly believe the table only has customer/vendor/reason data and miss status entirely.

## Minor Observations

- Revenue chart Y-axis increments are non-round (S/0, 700, 1400, 2100, 2800) instead of a cleaner scale (0/1000/2000/3000) — reads as an unstyled default rather than a chosen scale.
- The risk-level filter dropdown options ("Alto"/"Medio"/"Bajo") are plain text with no color swatch, even though every other place these same three levels appear (badges, score-circle rings) is color-coded — a cheap, missed consistency win.
- The admin alerts table has a lot of empty white space below only 3 rows on desktop, with no footer/pagination/"showing 3 of 3" — may just be sparse mock data, but reads unfinished.
- Bottom mobile nav bar has no safe-area-inset padding accounted for beyond what was already added — worth a real-device check (not just browser emulation) before shipping.
- The donut/bar chart SVGs render as bare `img`/`application` roles with no data-table fallback for screen readers, unlike `ScoreCircle`'s explicit `aria-label` pattern, which is worth replicating.

## Questions to Consider

- If sellers are "not expected to live inside this tool all day," why does the primary interaction model (browse a list, click a card, read a paragraph) look identical to a tool built for someone who does live in it all day — what would this screen look like optimized for a 10-second glance instead of a dashboard session?
- The AI-generated summary and required action are the actual product value, yet they're the same visual weight as a phone number — what happens if the card is redesigned around the summary as the hero element instead of the customer identity block?
- Both the risk score and the audit "Estado" are opaque, system-derived judgments with zero explanation anywhere in the UI — is a "why" affordance missing because it's hard to explain the model, or because nobody's asked yet?
